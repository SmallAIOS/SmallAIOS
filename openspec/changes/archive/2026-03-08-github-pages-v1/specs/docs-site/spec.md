## ADDED Requirements

### Requirement: Dark-mode glass theme with Furo base
The documentation site SHALL use the Furo Sphinx theme configured for dark mode as the default appearance. Custom CSS SHALL apply a glass/translucent effect to the sidebar and content areas using `backdrop-filter: blur(12px)`, `background: rgba(30, 30, 40, 0.75)`, and `border: 1px solid rgba(255, 255, 255, 0.08)`. The color scheme SHALL use dark backgrounds (#1a1a2e base, #16213e secondary) with light text (#e0e0e0) and accent colors for links and headings.

#### Scenario: Site renders with dark glass appearance
- **WHEN** a user visits the documentation site in a modern browser
- **THEN** the page background is dark (#1a1a2e or similar), the sidebar and content panels have a frosted glass translucent appearance, and text is light-colored with sufficient contrast (WCAG AA compliant)

#### Scenario: Backdrop-filter applies on supported browsers
- **WHEN** the browser supports `backdrop-filter` CSS property
- **THEN** the sidebar and main content area display a blur effect behind semi-transparent surfaces, creating a glass/frosted appearance

#### Scenario: Graceful fallback on unsupported browsers
- **WHEN** the browser does not support `backdrop-filter`
- **THEN** the sidebar and content areas fall back to opaque dark backgrounds without the blur effect, maintaining readability

### Requirement: RTD-style sidebar with collapsible navigation
The documentation site SHALL display a left sidebar with hierarchical, collapsible navigation sections following the Read the Docs style. The sidebar SHALL include the project logo/title at the top, a search box, and expandable/collapsible toctree sections. Navigation items SHALL highlight the current page.

#### Scenario: Sidebar displays hierarchical navigation
- **WHEN** a user visits any documentation page
- **THEN** the left sidebar displays all top-level toctree entries with expandable subsections matching the document hierarchy

#### Scenario: Current page is highlighted
- **WHEN** a user is viewing a specific documentation page
- **THEN** the corresponding sidebar entry is visually highlighted (distinct background or border color) and its parent sections are expanded

#### Scenario: Sections are collapsible
- **WHEN** a user clicks on a sidebar section header that has children
- **THEN** the section toggles between expanded (showing children) and collapsed (hiding children) states

### Requirement: Responsive mobile-friendly layout
The documentation site SHALL be responsive and usable on mobile devices (viewport width < 768px). On small screens, the sidebar SHALL collapse into a hamburger menu overlay, and content SHALL fill the full viewport width.

#### Scenario: Mobile viewport hides sidebar
- **WHEN** the viewport width is less than 768px
- **THEN** the sidebar is hidden by default and a hamburger/menu toggle button is visible in the header area

#### Scenario: Mobile menu toggle reveals navigation
- **WHEN** a user taps the hamburger menu button on a mobile device
- **THEN** the sidebar slides in as an overlay showing the full navigation tree, and tapping outside or on a link closes it

#### Scenario: Content is readable on mobile
- **WHEN** the viewport width is less than 768px
- **THEN** the main content area fills the full width, text wraps appropriately, code blocks are horizontally scrollable, and PlantUML diagrams scale or scroll

### Requirement: Sphinx-needs traceability tables rendered in documentation
The documentation site SHALL render all sphinx-needs directives (req, spec, impl, test, design) as styled tables with color-coded type indicators. Traceability matrices generated by `needtable`, `needflow`, and `needlist` directives SHALL be fully functional in the built HTML.

#### Scenario: Requirements render with type styling
- **WHEN** the site is built and a page contains `.. req::` directives
- **THEN** each requirement is rendered as a styled card/block with the REQ_ prefix, the configured color (#BFD8D2), title, description, and any linked items

#### Scenario: Traceability matrix is navigable
- **WHEN** a user views the traceability page
- **THEN** a `needtable` or `needlist` displays all requirements with clickable links to their definitions, and `needflow` diagrams render as SVG graphs showing requirement relationships

#### Scenario: Extra options are displayed
- **WHEN** a sphinx-needs item has `safety_level`, `coverage`, or `verification_method` set
- **THEN** these extra fields are visible in the rendered item alongside the standard fields

### Requirement: PlantUML diagrams render as SVG
The documentation site SHALL render all PlantUML diagrams embedded in RST files as inline SVG images. The rendering SHALL use the PlantUML public server (`https://www.plantuml.com/plantuml/svg/`). SVG output SHALL be used for crisp rendering at all zoom levels.

#### Scenario: Architecture diagram renders
- **WHEN** the site builds and `architecture.rst` includes a `.. uml::` directive referencing `architecture.puml`
- **THEN** the resulting HTML page contains an inline SVG image of the architecture diagram

#### Scenario: PlantUML server unavailable
- **WHEN** the PlantUML public server is temporarily unreachable during a build
- **THEN** the build completes with a warning (not an error), and affected diagrams show a placeholder or text representation

### Requirement: Page structure covers all documentation areas
The documentation site SHALL have the following top-level pages accessible from the sidebar navigation: (1) Landing/home page with project overview, (2) Architecture overview with system diagrams, (3) Getting Started guide with build and deployment instructions, (4) API Reference placeholder page, (5) Requirements and traceability section with sphinx-needs content, (6) Changelog page reflecting the project CHANGELOG.md.

#### Scenario: All top-level pages are accessible
- **WHEN** a user visits the documentation site and expands the sidebar
- **THEN** all six top-level sections are visible and clickable: Home, Architecture, Getting Started, API Reference, Requirements, Changelog

#### Scenario: Landing page provides project overview
- **WHEN** a user visits the root URL of the documentation site
- **THEN** the landing page displays the project name, a brief description of SmallAIOS, key features, and navigation to subsections

#### Scenario: Existing content is preserved
- **WHEN** the site is built
- **THEN** all existing RST content (architecture.rst, requirements.rst, traceability.rst) and markdown files (bare-metal-deployment.md, local-testing.md, boot-security-matrix.md, misra-rust-policy.md) are included in the built output and accessible via navigation

### Requirement: Markdown and RST coexistence via myst-parser
The documentation site SHALL support both reStructuredText (.rst) and Markdown (.md) source files. Markdown support SHALL be provided by the myst-parser extension. Existing markdown files in the `docs/` directory SHALL be automatically included in the Sphinx build.

#### Scenario: Markdown files are built
- **WHEN** the Sphinx build runs
- **THEN** all `.md` files referenced in toctrees are processed by myst-parser and rendered as HTML pages

#### Scenario: Cross-references between formats work
- **WHEN** an RST file references a markdown file via toctree or cross-reference
- **THEN** the link resolves correctly in the built HTML
