## 7. `std`-IO adapter (`TcpTlsStream`)

- [x] 7.1 `tls-client/src/std_io/mod.rs` — `TcpTlsStream` wrapping `std::net::TcpStream` *(behind a new `std` feature; the crate core stays `#![no_std]`. Generic `TlsStream<T: Read + Write>` carries the data-phase logic so it's testable over a mock socket; `TcpTlsStream` is the `TcpStream` alias)*
- [x] 7.2 `TcpTlsStream::connect(host, port, config) -> Result<Self, TlsClientError>` — drives the handshake state machine over the TCP socket *(entropy drawn from the hardware-seeded `security` CSPRNG. **Bounded by `TlsTimeouts`, added on review of the Phase 8 PR:** `connect` previously called `TcpStream::connect` with no deadline and then ran the handshake over a socket with no `SO_RCVTIMEO`/`SO_SNDTIMEO`, so a peer that completed the TCP handshake and went silent parked the caller — and with it the whole audit-export pipeline — indefinitely. `connect` now applies `TlsTimeouts::default()` (10 s connect, 30 s per read/write) and `connect_with_timeouts` takes explicit deadlines; the connect budget is shared across every resolved address rather than spent per-address. `Duration::ZERO` means unbounded. Timeouts surface as `TcpConnect`/`Io`, which 7.4 already classifies `Retry`, so backoff handles them with no new error variant and no API break. **Not covered:** `ToSocketAddrs` name resolution — `std` cannot bound it without a resolver thread; documented on the type. **Follow-on:** the deadlines are a `container` constant (`TLS_TIMEOUTS`), not `immudb.toml` keys; promoting them to operator config needs schema, validation bounds, and spec deltas, deliberately not folded into Phase 8.)*
- [x] 7.3 Implement `Read`, `Write`, and the existing `container::audit_export_runtime::transport::TlsStreamLike` trait (with `close()` sending `close_notify`) *(`Read`/`Write`/`close` live here; the `TlsStreamLike` bridge impl belongs in `container` per the layer model — Layer 1 `tls-client` cannot depend on Layer 3 `container` — so it lands with Phase 8)*
- [x] 7.4 Map `TlsClientError` → `TransportError`: TcpConnect / Io / BadHandshake → `Retry`; everything else → `HardFail` *(landed as `map_tls_error` + `tls_retry_class` in `container::audit_export_runtime::transport`. **Split into two functions deliberately:** `TransportError` has a single `TlsHandshake` variant, so the mapping is lossy — a retryable `BadHandshake` and a terminal `ChainUntrusted` both collapse onto it and the Retry/HardFail distinction cannot survive. `tls_retry_class` returns the classification from the `TlsClientError` before conversion; a test asserts the two map identically while classifying differently, so the lossiness is pinned rather than latent. **Follow-on:** nothing consumes `tls_retry_class` yet — `ClientError::Transport` has no retry classification in the pipeline (only gRPC statuses do, via `RetryClass`), so honouring the class end-to-end needs either a new `TransportError` variant or a `TransportError → RetryClass` mapping in `audit-export`. Tracked with 8.3/8.4.)*
