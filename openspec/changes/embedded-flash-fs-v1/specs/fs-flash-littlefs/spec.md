## ADDED Requirements

### Requirement: littlefs v2.x read path
The `fs` crate SHALL provide a clean-room `#![no_std]` Rust reader for the littlefs v2.x on-disk format pinned to a specific spec commit hash documented in `docs/embedded-flash-fs.md`. The reader SHALL parse: superblock, metadata pairs, directory entries, file inline data, file CTZ block lists, and global state. The reader SHALL refuse to mount images of any other major version with `Err: littlefs major version <n> unsupported, reflash required`.

#### Scenario: littlefs v2 image mounts
- **WHEN** a littlefs v2.x image produced by `mklittlefs` is presented
- **THEN** mount SHALL succeed and the directory tree SHALL be readable

#### Scenario: Older v1 image rejected
- **WHEN** a littlefs v1 image is presented
- **THEN** mount SHALL fail with `Err: littlefs major version 1 unsupported, reflash required`
- **AND** the message SHALL name the reflash tooling

#### Scenario: Round-trip vs littlefs2 Rust port
- **WHEN** an image generated by the `littlefs2` dev-dependency crate is mounted by SmallAIOS
- **THEN** every file's contents SHALL match `cmp`-byte-for-byte

### Requirement: littlefs v2.x write path
The `fs` crate SHALL provide a clean-room `#![no_std]` Rust writer for littlefs v2.x. The writer SHALL implement: file create, directory create, write extending a file, file deletion, directory deletion, atomic rename via metadata-pair commit, truncate. Writes SHALL go through littlefs's metadata-pair commit semantics so the format's natural power-fail safety holds.

#### Scenario: Write then external read
- **WHEN** SmallAIOS creates `/flash/foo` with known bytes
- **AND** the partition is read by `littlefs-fuse` on a recovery laptop
- **THEN** the recovery tool SHALL read back the same bytes

#### Scenario: Atomic rename preserves consistency
- **WHEN** SmallAIOS performs `rename(src, dst)` while another reader has `dst` open
- **THEN** the open reader's file handle SHALL refer to the original `dst` content for the rest of its lifetime
- **AND** new opens of `dst` SHALL see `src`'s content

### Requirement: fsync and metadata-pair commit
`fsync(fd)` SHALL force all dirty pages of `fd` and the corresponding metadata-pair updates to flash via littlefs's commit operation before returning. After successful `fsync`, the data SHALL be durable across an arbitrary power loss. There SHALL be no background timer-driven commit on littlefs (unlike F2FS); operators that need durability call `fsync` explicitly. (Rationale: flash devices have higher per-erase cost; spurious commits accelerate wear.)

#### Scenario: fsync survives power loss
- **WHEN** SmallAIOS writes a file, calls `fsync`, then the system loses power
- **AND** the partition is read on next boot
- **THEN** the fsync'd file content SHALL be intact

#### Scenario: Non-fsync data lost up to last commit
- **WHEN** SmallAIOS writes data without calling `fsync` and power is lost
- **THEN** the data MAY be absent on next mount
- **AND** the filesystem SHALL still be consistent

#### Scenario: Commit atomicity invariant (Kani-modeled)
- **WHEN** the system loses power at any point during a metadata-pair commit
- **THEN** on next mount the kernel SHALL find at least one metadata-pair half that is valid and has the correct generation counter
- **AND** the FS SHALL be mountable

### Requirement: Wear-leveling integration
The littlefs writer SHALL use the format's built-in dynamic wear-leveling pool. Default parameters SHALL be: `lookahead_size=8192`, `cache_size=block_size`, `block_cycles=500`. These defaults SHALL NOT be operator-configurable in v1 — exposing them is documented as a future evolution path.

The TLA+ model `littlefs_wear.tla` SHALL prove the wear-leveling progress invariant: every block is eventually erased before any specific block exceeds its `block_cycles` budget under any valid program/erase sequence.

#### Scenario: 1M-cycle stress shows even distribution
- **WHEN** the mock device runs 1M program/erase cycles via `model_add` / overwrites
- **THEN** the per-block erase counts SHALL be within 5% of each other (mean ± 2σ)
- **AND** no block SHALL have exceeded `block_cycles`

#### Scenario: Block reaching cycle budget rotated out
- **WHEN** a block's erase counter reaches `block_cycles - 50` (within 10% of budget)
- **THEN** the allocator SHALL prefer cooler blocks for new writes
- **AND** the hot block SHALL eventually be skipped

### Requirement: Bad Block Table integration
The littlefs writer SHALL consult the BBT before allocating any block. Blocks marked bad SHALL be skipped; the allocator SHALL transparently use the next valid block. Runtime-detected bad blocks (program failure, erase failure) SHALL be added to the BBT, and the BBT update SHALL be committed before the operation returns.

#### Scenario: Erase failure marks block bad
- **WHEN** `erase(block 42)` returns `Err(FlashError::EraseFailure)`
- **THEN** block 42 SHALL be added to the BBT
- **AND** both BBT copies SHALL be updated
- **AND** subsequent allocations SHALL skip block 42

### Requirement: Format-on-first-boot with physical presence
When `/flash/` is unformatted on first boot AND a `PhysicalPresenceProvider` indicator asserts, the kernel SHALL run an in-process `mklittlefs`-equivalent to format the partition with the current default parameters. When the partition is unformatted and physical presence is NOT asserted, the kernel SHALL halt with a recovery hint pointing at the per-arch presence-assertion mechanism.

#### Scenario: Format with presence asserted
- **WHEN** the flash partition has no littlefs superblock and the GPIO presence pin is asserted
- **THEN** the kernel SHALL format the partition, mount it, and append a `flash_format` audit record

#### Scenario: Halt without presence
- **WHEN** the flash partition has no littlefs superblock and no presence provider asserts
- **THEN** the kernel SHALL halt with `Err: /flash/ unformatted; assert physical presence to format`
