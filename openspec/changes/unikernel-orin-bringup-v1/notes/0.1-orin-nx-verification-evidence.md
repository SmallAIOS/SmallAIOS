## KVM — proposal assumption needs adjustment

```
$ lsmod | grep -i kvm
(no output)

$ modinfo kvm
name:           kvm
filename:       (builtin)
license:        GPL
file:           arch/arm64/kvm/kvm
author:         Qumranet

$ ls -la /dev/kvm
crw-rw----+ 1 root kvm 10, 232 Mar 24 14:52 /dev/kvm

$ ls /sys/module/ | grep -i kvm
kvm
```

**Finding:** KVM is **compiled into the kernel** on JetPack 6.1, not built as a loadable module. `lsmod | grep kvm` returning empty is the **correct** state — there's nothing to load. `/dev/kvm` is present, `/sys/module/kvm` is present, KVM is fully operational.

**Action for Phase 1:**
- Task 0.3 wording ("Confirm `kvm` module is loaded — if not, document the `modprobe kvm` workaround") is wrong for JetPack 6. The right check is **`[ -c /dev/kvm ]`** (character device exists). `modprobe kvm` is a no-op on builtin KVM; the workaround section would mislead users.
- Update task 0.3 to: "Confirm `/dev/kvm` exists (Phase 1 prerequisite). On JetPack 6 KVM is builtin; if `/dev/kvm` is missing, the running kernel is non-standard — escalate."
- The Phase 1 quickstart (`docs/jetson-kvm-quickstart.md`, task 1.8) and the smoke script (`scripts/test-jetson-kvm.sh`, task 1.2) should both probe `/dev/kvm` rather than `lsmod`.
- Phase 1 acceptance unblocked: KVM works.

## Build artifact correction (proposal task 1.1 errata)

The proposal narrates `cargo build --target aarch64-unknown-none -p smallaios-kernel --release` producing `target/aarch64-unknown-none/release/smallaios-kernel.bin`. Repo inspection contradicts this on two counts:

| Item | Proposal | Actual |
|------|----------|--------|
| Crate (`-p`) | `smallaios-kernel` | `smallaios-arch-aarch64` |
| Artifact name | `smallaios-kernel.bin` | `smallaios-aarch64` |

Evidence: `arch/aarch64/Cargo.toml` declares `[[bin]] name = "smallaios-aarch64" path = "src/main.rs"`; the `kernel` crate is a host-testable library with no `[[bin]]`. The existing `build-kernel-arm` Justfile recipe uses `-p smallaios-arch-aarch64`; `run-arm` boots `target/aarch64-unknown-none/release/smallaios-aarch64`. The Phase 1 `run-jetson-kvm` recipe should depend on `build-kernel-arm` rather than re-spell the build incantation.

## Build host: Mac-Apple-Silicon as workstation

The target `aarch64-unknown-none` is freestanding (`no_std`, no libc, no OS-level deps). `rustc` + `cargo` on `aarch64-apple-darwin` cross-compile to it without any C cross toolchain — `rust-lld` (LLVM linker, comes with the `llvm-tools` rustup component the project pins) handles the link. This means the recommended Phase 1 workflow is:

- **Workstation:** Mac-Apple-Silicon. Hosts the Rust toolchain, the repo, the editor. Builds `smallaios-aarch64` via `cargo build --release --target aarch64-unknown-none -p smallaios-arch-aarch64`. Cold-cache build ≈ 2 min on M-series; incremental ≈ 5–30 s.
- **Runner:** Orin NX (this box). Hosts qemu, KVM, the kernel binary, the serial output. **Does not need the Rust toolchain installed at all.**
- **Glue:** `scp` from Mac to Orin (or the `just run-jetson-kvm $SSH_HOST` recipe wraps it).

This is the embedded-development pattern (workstation builds, target executes) and matches the `SSH_HOST` arg the proposal already designed into the recipe shape. CI does the equivalent on `ubuntu-latest` x86_64 every PR; Mac-arm64 is a closer-to-target permutation.

The alternative — install Rust toolchain on the Orin — works (cargo + rustup aarch64-unknown-linux-gnu binaries exist, ~2 GB on disk, ~5 min one-time setup) but couples a "clean test target" with a "dev environment". The recommended workflow keeps the Orin minimal.
