# Delta for Safety-Critical Development Standards

## ADDED Requirements

### Requirement: NIST SP 800-53 CA (Security Assessment) Cross-References with DO-178C Verification Objectives

The safety-critical development standards SHALL cross-reference NIST SP 800-53 Rev 5 CA (Security Assessment and Authorization) controls with DO-178C DAL A verification objectives. The cross-reference SHALL map: CA-2 (Control Assessments) to DO-178C objective A-7 (Verification of Verification Process Results), ensuring that security control assessments and DO-178C verification reviews share evidence artifacts where applicable; CA-7 (Continuous Monitoring) to DO-178C objective A-8 (Configuration Management Process), ensuring that ongoing security posture monitoring and configuration audits produce artifacts usable for both frameworks; and CA-8 (Penetration Testing) to DO-178C robustness testing objectives, ensuring that security penetration test results supplement the DO-178C robustness test suite.

#### Scenario: CA-2 mapped to DO-178C verification objective A-7

- WHEN both NIST SP 800-53 CA-2 (Control Assessments) and DO-178C objective A-7 (Verification of Verification Process Results) apply to a SmallAIOS component
- THEN the documentation MUST provide a cross-reference entry identifying the shared verification artifacts (test results, coverage reports, formal verification proofs)
- AND the entry MUST specify whether a single artifact satisfies both CA-2 assessment evidence and A-7 verification results, or whether supplementary artifacts are required
- AND any gaps where CA-2 requires evidence not produced by the DO-178C A-7 process MUST be documented with planned supplementary activities

#### Scenario: CA-7 mapped to DO-178C configuration management objective A-8

- WHEN both NIST SP 800-53 CA-7 (Continuous Monitoring) and DO-178C objective A-8 (Configuration Management Process) apply
- THEN the documentation MUST identify shared configuration management artifacts (baselines, change logs, version control records) that serve as evidence for both CA-7 monitoring and A-8 configuration audits
- AND the cross-reference MUST document the monitoring cadence required by CA-7 and confirm it meets or exceeds the DO-178C A-8 audit frequency

#### Scenario: CA-8 mapped to DO-178C robustness testing

- WHEN NIST SP 800-53 CA-8 (Penetration Testing) is required for a SmallAIOS deployment
- THEN the cross-reference MUST map penetration test objectives to DO-178C robustness testing categories (normal range, abnormal range, and stress testing)
- AND penetration test results that expose robustness failures MUST be traceable to DO-178C problem reports and corrective actions
- AND the combined test suite MUST demonstrate coverage of both security attack vectors (CA-8) and operational robustness scenarios (DO-178C)

#### Scenario: Cross-reference table completeness validation

- WHEN the CA-to-DO-178C cross-reference table is reviewed
- THEN every NIST SP 800-53 CA family control (CA-1 through CA-9) MUST have either a mapped DO-178C objective, a documented justification for no mapping, or an explicit "Not Applicable" designation
- AND every DO-178C DAL A verification objective (A-1 through A-10) that has a security dimension MUST be cross-referenced to the applicable CA control

### Requirement: Security-Specific MC/DC Coverage for Cryptographic and Capability Paths

The safety-critical development process SHALL require 100% Modified Condition/Decision Coverage (MC/DC) for all cryptographic code paths and all capability check code paths. Cryptographic code paths include all functions in the `security/src/crypto/` module tree: key generation, key encapsulation/decapsulation, signing/verification, symmetric encryption/decryption, hashing, CSPRNG operations, and constant-time utility functions. Capability check code paths include all functions in `security/src/capability.rs`, `security/src/registry.rs`, and `security/src/policy.rs` that evaluate, grant, revoke, delegate, or enforce capabilities.

#### Scenario: Cryptographic signing path achieves 100% MC/DC

- WHEN the MC/DC coverage report is generated for the ML-DSA-65 signing and verification functions in `security/src/crypto/ml_dsa.rs`
- THEN the report MUST show 100% MC/DC coverage — every condition in every decision independently affects the decision outcome in at least one test case
- AND coverage MUST include all error handling branches (invalid key, malformed signature, verification failure)
- AND the coverage report MUST be generated by a DO-330 TQL-5 qualified tool (cargo-llvm-cov with LLVM MC/DC instrumentation)

#### Scenario: Cryptographic encryption path achieves 100% MC/DC

- WHEN the MC/DC coverage report is generated for the AES-256-GCM encryption and decryption functions in `security/src/crypto/aes_gcm.rs`
- THEN the report MUST show 100% MC/DC coverage
- AND coverage MUST include all branches for hardware acceleration detection (AES-NI present vs. software fallback) and all error conditions (authentication tag mismatch, buffer size errors)

#### Scenario: Capability enforcement path achieves 100% MC/DC

- WHEN the MC/DC coverage report is generated for the capability enforcement logic in `security/src/capability.rs` and `security/src/policy.rs`
- THEN the report MUST show 100% MC/DC coverage for all permission check decisions (READ, WRITE, EXECUTE, GRANT)
- AND coverage MUST include all branches for capability expiry checking, resource type matching, permission bitmask evaluation, and delegation chain validation

#### Scenario: Coverage regression blocks release

- WHEN a code change reduces MC/DC coverage below 100% for any cryptographic or capability check code path
- THEN the CI pipeline MUST fail the build
- AND the failure report MUST identify the specific uncovered condition(s) and the responsible code change
- AND the build MUST NOT be releasable until 100% MC/DC coverage is restored

### Requirement: OT Functional Safety Cross-Reference Table

The safety-critical development standards SHALL include a cross-reference table mapping SmallAIOS kernel components to IEC 61508 Safety Integrity Levels (SIL) and ISO 26262 Automotive Safety Integrity Levels (ASIL). The mapping SHALL cover: kernel core (memory management, scheduler, syscall interface) at SIL 3 / ASIL D; capability-based security system at SIL 3 / ASIL D; cryptographic subsystem at SIL 2 / ASIL C; ONNX runtime (session management, operator dispatch) at SIL 3 / ASIL D; IPC messaging at SIL 2 / ASIL C; watchdog and real-time subsystem at SIL 3 / ASIL D; and device HAL at SIL 2 / ASIL C. Each mapping entry SHALL identify the applicable IEC 61508 Part 3 technique and ISO 26262 Part 6 method used to achieve the assigned level.

#### Scenario: Kernel core mapped to SIL 3 / ASIL D

- WHEN the OT functional safety cross-reference is reviewed for the kernel core (memory management, scheduler, syscall interface)
- THEN the entry MUST assign SIL 3 (IEC 61508) and ASIL D (ISO 26262)
- AND MUST identify the applicable IEC 61508 Part 3 techniques: semi-formal methods (TLA+ scheduling proofs), MC/DC structural coverage, defensive programming (Rust memory safety), and static analysis (Clippy with MISRA-Rust rules)
- AND MUST identify the applicable ISO 26262 Part 6 methods: requirements-based testing, structural coverage at MC/DC level, and formal verification of critical properties

#### Scenario: Cryptographic subsystem mapped to SIL 2 / ASIL C

- WHEN the OT functional safety cross-reference is reviewed for the cryptographic subsystem
- THEN the entry MUST assign SIL 2 (IEC 61508) and ASIL C (ISO 26262)
- AND MUST justify the assignment: cryptographic failures affect confidentiality and integrity but are mitigated by redundant verification (hybrid mode) and do not directly cause physical safety hazards in the absence of a compromised adversary
- AND MUST identify applicable techniques: NIST test vector validation, constant-time implementation verification (dudect), and MC/DC coverage at 100%

#### Scenario: ONNX runtime mapped to SIL 3 / ASIL D

- WHEN the OT functional safety cross-reference is reviewed for the ONNX runtime
- THEN the entry MUST assign SIL 3 (IEC 61508) and ASIL D (ISO 26262)
- AND MUST justify the assignment: incorrect inference results from runtime errors could lead to unsafe actuator commands in autonomous vehicle or industrial control deployments
- AND MUST identify applicable techniques: requirements-based testing, fuzz testing of model parsing, MC/DC coverage, and WCET analysis for inference paths

#### Scenario: Cross-reference table completeness

- WHEN the OT functional safety cross-reference table is reviewed for completeness
- THEN every SmallAIOS kernel crate (kernel, arch/x86_64, arch/aarch64, arch/nvidia, onnx-rt, ipc, net, security, posix, container) MUST have an entry with both an IEC 61508 SIL assignment and an ISO 26262 ASIL assignment
- AND each entry MUST include a justification for the assigned level and a list of applicable safety techniques

#### Scenario: SIL/ASIL assignment drives verification rigor

- WHEN a kernel component is assigned SIL 3 / ASIL D
- THEN the verification plan for that component MUST require MC/DC 100% structural coverage, requirements-based testing with full traceability, and at least one formal method (TLA+, Lean 4, or SPIN)
- AND WHEN a kernel component is assigned SIL 2 / ASIL C
- THEN the verification plan MUST require at minimum branch coverage at 100% and requirements-based testing with full traceability

### Requirement: Security Test Categories

The safety-critical development process SHALL define and enforce four security-specific test categories: capability bypass testing, cryptographic implementation validation, timing side-channel testing, and resource exhaustion testing. Each category SHALL have defined test methodologies, pass/fail criteria, and integration into the CI pipeline.

#### Scenario: Capability bypass testing

- WHEN the security test suite executes capability bypass tests
- THEN the test suite MUST include tests that attempt to: forge a capability token by constructing a Capability struct with arbitrary fields; access a resource without holding any capability; access a resource with an expired capability; access a resource with insufficient permissions (e.g., WRITE when only READ is held); delegate a capability without the GRANT permission; and access a resource type outside the task's information flow policy
- AND every bypass attempt MUST be denied by the capability system
- AND every denial MUST produce an audit log entry
- AND the test suite MUST achieve 100% coverage of all capability enforcement decision points

#### Scenario: Cryptographic implementation validation with NIST test vectors

- WHEN the security test suite executes cryptographic validation tests
- THEN the test suite MUST validate each cryptographic algorithm against its official NIST test vectors: ML-KEM-768 against FIPS 203 Known Answer Tests (KATs), ML-DSA-65 against FIPS 204 KATs, AES-256-GCM against NIST SP 800-38D test vectors, SHA-3-256 against NIST FIPS 202 test vectors, and SHAKE256 against NIST FIPS 202 test vectors
- AND every test vector MUST produce the expected output exactly (byte-for-byte match)
- AND failure on any single test vector MUST fail the entire test suite

#### Scenario: Timing side-channel testing with dudect methodology

- WHEN the security test suite executes timing side-channel tests
- THEN the test suite MUST apply the dudect statistical methodology (Welch's t-test on execution time distributions) to all constant-time cryptographic functions: AES-256-GCM encrypt/decrypt, ML-KEM encapsulation/decapsulation, ML-DSA signing/verification, SHA-3 hashing, SHAKE256 XOF, X25519 scalar multiplication, and Ed25519 signing
- AND the test MUST execute at minimum 10,000 measurements per function with two distinct input classes (e.g., all-zero vs. random)
- AND the Welch's t-test statistic MUST NOT exceed the threshold |t| < 4.5 for any function (indicating no statistically significant timing difference)
- AND any function exceeding the threshold MUST be flagged as a timing side-channel vulnerability and MUST block the release

#### Scenario: Resource exhaustion testing

- WHEN the security test suite executes resource exhaustion tests
- THEN the test suite MUST include tests that attempt to: exhaust heap memory by requesting allocations up to the configured limit; exhaust the tensor pool by allocating tensors until the pool is full; exceed the maximum concurrent inference request count; exceed the maximum TCP connection count; exceed the maximum IPC message size; and flood the capability system with rapid grant/revoke cycles
- AND each exhaustion attempt MUST be handled gracefully: the system MUST return an appropriate error code, MUST NOT crash or panic, and MUST continue servicing existing requests
- AND each exhaustion event MUST produce an audit log entry with the resource type and the requesting task ID

#### Scenario: Security test categories integrated into CI

- WHEN a pull request or merge to the main branch triggers the CI pipeline
- THEN the CI pipeline MUST execute all four security test categories (capability bypass, crypto validation, timing side-channel, resource exhaustion) as part of the standard test suite
- AND failure in any security test category MUST block the merge
- AND the CI report MUST include a summary of each category's pass/fail status with detailed failure information for any failing tests
